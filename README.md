# RedScribe Docs

**Live at [redscribe-labs.github.io/redscribe-docs](https://redscribe-labs.github.io/redscribe-docs/).**

The documentation site for [RedScribe](https://github.com/redscribe-labs/redscribe), self-hosted
engagement, finding, checklist, and report management for penetration
testing teams. Kept as its own isolated project, separate from the app's
repo, so the docs site has its own history, its own deploy target, and never
depends on the app repo being checked out.

## Structure

```
redscribe-docs/
├── site-src/     # EDIT HERE, an Astro + Starlight project (markdown source, theme, config)
└── docs/         # BUILT OUTPUT, static HTML generated by `npm run build`, committed
```

Two directories, on purpose:

- **`site-src/`** is where you work. Every page is a markdown file under
  `site-src/src/content/docs/`. See `site-src/README.md` for the project
  layout, dev commands, and how the color theme is wired up.
- **`docs/`** is generated, not hand edited. `astro.config.mjs` sets
  `outDir: '../docs'`, so `npm run build` writes the static site straight
  here. It's committed, not gitignored, specifically so GitHub Pages can
  serve it directly from a `/docs` folder on `main`, with no CI build step
  required.

## Building

Requires **Node.js ≥22.12.0** (Astro 7 and Starlight's hard floor, a plain
`npm install`/`npm run build` will fail on anything older, not just warn).
If your system Node is too old and you'd rather not touch it, grab a
standalone build and use it just for this project instead of changing
anything system-wide:

```sh
mkdir -p .tools && cd .tools
curl -fsSL -o node.tar.xz "https://nodejs.org/dist/v22.23.2/node-v22.23.2-linux-x64.tar.xz"
tar -xf node.tar.xz && mv node-v22.23.2-linux-x64 node22 && rm node.tar.xz
cd ..
export PATH="$PWD/.tools/node22/bin:$PATH"   # do this in every new shell before building
```

`.tools/` is gitignored, it's a local convenience, not something to commit.

Then, from `site-src/`:

```sh
cd site-src
npm install      # first time only
npm run build     # writes into ../docs
```

Preview the built output locally before committing it:

```sh
npm run preview
```

Or run the live reloading dev server while writing (doesn't touch `../docs`
until you build):

```sh
npm run dev
```

## Publishing to GitHub Pages

Already live. This repo is public, and `Settings → Pages` is set to
**Deploy from a branch**, branch `main`, folder `/docs`. To ship a change:

1. Edit under `site-src/`, run `npm run build`, then commit the resulting
   changes in both `site-src/` and `docs/`, and push. GitHub Pages picks
   up the new `docs/` content automatically, usually within a minute or two.

Two gotchas already bit this exact setup once each, worth knowing if you're
repeating this elsewhere:

- **`base` and `site` in `astro.config.mjs` must match the real Pages URL.**
  This is hosted as a project page
  (`https://redscribe-labs.github.io/redscribe-docs/`, not a custom domain
  and not a `redscribe-labs.github.io` user repo), so `base: '/redscribe-docs'`
  and the matching `site:` are already set there. Skipping this makes every
  internal link 404 on the live site while still working fine in local
  preview, since local preview serves from the domain root instead.
- **`docs/.nojekyll` must exist**, along with `site-src/public/.nojekyll` so
  it survives every rebuild. GitHub Pages runs Jekyll by default on "Deploy
  from a branch," and Jekyll silently strips any directory starting with an
  underscore, which is exactly what Astro names its asset output
  (`_astro/`). Without `.nojekyll`, pages load as bare unstyled HTML with
  every CSS and JS request 404ing, while the HTML itself serves fine. That
  combination makes it a confusing failure to diagnose from the symptom
  alone.

## Relationship to the app repo

This project treats [RedScribe's own
repo](https://github.com/redscribe-labs/redscribe) as a source of facts
only. `COLOR_SCHEME.md` for the theme, and the README, `BUILD.md`,
`CONTRIBUTING.md`, `docs/*.md`, and source code for content, but nothing
here is generated automatically from it. If the app changes in a way that
makes a page here stale, a new feature, a changed env var, a renamed
permission, update the relevant page under `site-src/src/content/docs/` by
hand and rebuild.
