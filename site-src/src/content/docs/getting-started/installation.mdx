There are four ways to run RedScribe. The only real question is how much
TLS certificate setup you want to do yourself. Pick the row below that
matches your situation, follow its steps, and you'll land at the same
place either way: [First run](/getting-started/first-run/), where you
generate the instance's encryption key and create your first admin
account.

Just want to try it out first? The [Quickstart](/getting-started/quickstart/)
covers the same no-TLS setup as Method 3 below, in fewer words, for a
machine only you need to reach.

| Method | Best for | TLS |
|---|---|---|
| [1. Tailscale](#method-1-docker-compose--tailscale-recommended) | Fully automated HTTPS, zero certificate management | Automatic |
| [2. Your own certificate](#method-2-docker-compose--your-own-tls-certificate) | Your own domain, a certificate from anywhere | You supply it |
| [3. Plain HTTP](#method-3-docker-compose-plain-http) | Trying it out locally or on a private network | None |
| [4. Local development](#method-4-local-development-without-docker) | Working on RedScribe's own code | None (loopback only) |

## Before you start

Every method needs the same two secrets in place first, as file-based
Docker secrets rather than `.env` values (see [Environment
variables](/reference/environment-variables/) for why).

<Steps>
1. Copy the template:

   ```sh
   cp .env.example .env
   ```
2. Generate a random signing key for Django's own session and CSRF
   protection, straight into its secret file:

   ```sh
   python3 -c "import secrets, string; print(''.join(secrets.choice(string.ascii_letters + string.digits) for _ in range(50)))" > secrets/django_secret_key.txt
   ```
3. Put a database password of your own choosing into its own secret file:

   ```sh
   openssl rand -base64 32 > secrets/postgres_password.txt
   ```
4. Create an empty placeholder for the instance's root encryption key, so
   Compose has a file to mount. You'll fill in the real value in [First
   run](/getting-started/first-run/), after the app is up:

   ```sh
   touch secrets/root_key.txt
   ```
</Steps>

The instance's master encryption key, `REDSCRIBE_ROOT_KEY`, isn't
generated here (only the empty placeholder file above). It needs
RedScribe's own generator command, so it's covered in
[First run](/getting-started/first-run/) instead, after the app is up.

## Method 1: Docker Compose + Tailscale (recommended)

Choose this if the machine is already on a
[Tailscale](https://tailscale.com) network with MagicDNS and HTTPS
certificates turned on. RedScribe handles the certificate entirely from
there: no manual renewal, no certificate authority to deal with, nothing
else to configure.

<Steps>
1. In `.env`, set `NGINX_SERVER_NAME=<your-machine>.<tailnet>.ts.net` (find
   it by running `tailscale status --self --json` and reading the
   `DNSName` field), and add that same hostname to
   `DJANGO_ALLOWED_HOSTS`.
2. Set `DJANGO_SETTINGS_MODULE=config.settings.prod` in `.env`.
3. Start everything:

   ```sh
   docker compose --profile tailscale up -d --build
   ```
</Steps>

That's the whole setup. A background service requests the first
certificate and keeps renewing it for as long as the stack runs, and the
web server picks up each renewal automatically. Continue at
[First run](/getting-started/first-run/).

<Aside type="caution" title="Your tailnet hostname becomes publicly visible">
The certificate this method issues is a real, publicly trusted one, and
every certificate issued this way is recorded permanently in public logs
(Certificate Transparency). RedScribe itself stays reachable only from your
tailnet, but the hostname `<your-machine>.<tailnet>.ts.net` becomes
discoverable the moment that first certificate is issued. If that hostname
itself needs to stay private, use
[Method 2](#method-2-docker-compose--your-own-tls-certificate) instead.
</Aside>

Want it reachable from the public internet too, not just your tailnet? See
[exposing it with Tailscale
Funnel](/deployment/docker-compose/#exposing-it-beyond-your-tailnet-with-tailscale-funnel)
in the deployment deep dive.

## Method 2: Docker Compose + your own TLS certificate

Already have a certificate for your own domain, from Let's Encrypt, a
corporate certificate authority, or anywhere else? RedScribe picks it up
automatically, including future renewals, as long as it lands in the right
place.

<Steps>
1. In `.env`, set `NGINX_SERVER_NAME=<your-domain>`, add that domain to
   `DJANGO_ALLOWED_HOSTS`, and set
   `DJANGO_SETTINGS_MODULE=config.settings.prod`.
2. Copy your certificate files into place, using exactly these two
   filenames (see `certs/README.md` for details):

   ```sh
   cp /path/to/your/fullchain.pem certs/fullchain.pem
   cp /path/to/your/privkey.pem   certs/privkey.pem
   ```
3. Start everything:

   ```sh
   docker compose up -d --build
   ```
</Steps>

The web server waits for both files to exist before it starts, and reloads
automatically whenever it notices the certificate has changed. That means
your own renewal process, a certbot timer or whatever else you already
run, gets picked up within the hour without you touching this stack at
all. Continue at [First run](/getting-started/first-run/).

## Method 3: Docker Compose, plain HTTP

No TLS at all. Fine for trying things out locally or on a private network
you already trust. **Not fine for anything reachable beyond that.**

```sh
docker compose up -d --build
```

Leave `DJANGO_SETTINGS_MODULE` at its `.env.example` default
(`config.settings.dev`). Skip straight to `http://localhost:8000/`, which
is bound to the host machine only, rather than going through the web
server at all. Continue at [First run](/getting-started/first-run/).

## Method 4: Local development without Docker

For working on RedScribe's own code, without a full container rebuild
every time something changes:

<Aside type="note" title="No Docker secrets here, so everything is a plain .env value">
Methods 1-3 mount `DJANGO_SECRET_KEY`, `POSTGRES_PASSWORD`, and
`REDSCRIBE_ROOT_KEY` as file-based Docker secrets (see [Before you
start](#before-you-start)) — `_FILE`-suffixed env vars that point at a
file Compose mounts read-only at `/run/secrets/...`. There's no Compose
service here to mount anything, so that mechanism has nothing to read: set
all three as plain values directly in `.env` instead, the same fallback
path `env_secret()` already supports for bare-metal/CI (see [Environment
variables](/reference/environment-variables/)).
</Aside>

```sh
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
docker compose up -d db          # just the database
cp .env.example .env             # fill in DJANGO_SECRET_KEY/POSTGRES_PASSWORD as plain values, POSTGRES_HOST=localhost
python manage.py migrate
python manage.py generate_root_key   # put the output in .env as REDSCRIBE_ROOT_KEY
python manage.py bootstrap_superadmin --username admin --email admin@example.com
python manage.py runserver
```

This already creates the root key and the first admin account as part of
the same steps, so **skip [First run](/getting-started/first-run/)**, you're
done. See [Local development](/dev/local-development/) for the rest of the
day to day loop, including rebuilding frontend assets after a template or
CSS change.

## One thing worth knowing: how the web server sees your visitors

The web server container runs a little differently than you might expect,
in a way that matters for audit logs and login lockouts recording the
right IP address. See [why nginx uses host
networking](/deployment/docker-compose/#why-nginx-uses-host-networking) in
the deployment deep dive if you're curious.
