This page digs into how the Docker Compose stack actually works under the
hood: what each service does, why nginx is set up the way it is, how to
size the app's worker processes, and how to expose an instance beyond your
tailnet. For the step-by-step commands to bring an instance up in the first
place, see [Installation](/getting-started/installation/).

## The services

`docker-compose.yml` defines four services:

| Service | Image | Role |
|---|---|---|
| `db` | `postgres:17-alpine` | The database. Bound to `127.0.0.1:5432` on the host, for local admin access (`psql`, running migrations from the host). Never reachable off box. |
| `web` | Built from the repo's `Dockerfile` | The app itself, running under gunicorn. Bound to `127.0.0.1:8000` for direct host-side debugging, but `nginx` is the real public entry point. Mounts `./backups:/app/backups` as a plain host directory (not a named volume) so you can point `rsync` or `rclone` at it directly. |
| `nginx` | `nginx:1.27-alpine` | Handles TLS and reverse proxies to `web`. Runs with `network_mode: host`, see [below](#why-nginx-uses-host-networking) for why. |
| `cert-renew` | `tailscale/tailscale:v1.102.3` | Optional. Issues and renews a TLS certificate automatically via Tailscale. Only starts if you add `--profile tailscale`. |

A few things worth knowing about how these fit together:

- `web`'s root encryption key is mounted as a Docker **secret**
  (`redscribe_root_key`, backed by `./secrets/root_key.txt`), not an
  environment variable. See [Encryption model](/security/encryption/) for
  why that matters.
- `db` and `web` both have healthchecks, so `web` waits until `db` is
  actually ready (not just running) before it starts, and `nginx` waits on
  `web` the same way. `web`'s healthcheck pings a small `/health/` endpoint
  that checks the database connection.
- Bringing your own certificate? Skip `cert-renew` entirely, just run plain
  `docker compose up -d` and drop `fullchain.pem` and `privkey.pem` into
  `./certs` yourself. `nginx` doesn't care which path put them there. Using
  [Method 1](/getting-started/installation/#method-1-docker-compose--tailscale-recommended)
  instead? Add `--profile tailscale` to start `cert-renew` alongside
  everything else.

<Aside type="note" title="Why cert-renew runs as root">
`cert-renew` runs as the image's default root user rather than a pinned
host user. Root is always trusted by Tailscale's daemon for certificate
requests over the bind-mounted socket, the same trust `sudo` would give it
on the host directly. Root also avoids a permission error some users hit
on a brand-new host: Docker creates a freshly cloned `./certs` directory
as `root:root`, which a non-root process can't write into.
</Aside>

## Why nginx uses host networking

`nginx` runs with `network_mode: host` instead of a normal
`ports: - "80:80"` mapping. That means it binds the host's ports 80 and
443 directly, rather than going through Docker's own port forwarding.

This matters because RedScribe's login lockout and audit logging both
record the client's IP address. On a default Docker install, a
published-port mapping is relayed through a helper process that swaps in
its own address as the source of every connection. Without host
networking, every request would show up in the [audit
log](/security/audit-trail/) and [login lockout
tracking](/security/authentication/) with a meaningless Docker-internal
address instead of the real visitor's IP. Host networking sidesteps that
completely, with nothing to configure per host. `web`'s own
`127.0.0.1:8000` binding still works fine, since `nginx` and `web` now
share the host's own network.

<Aside type="note" title="One case this doesn't (and can't) change">
A request that originates *from the machine running Docker itself*, for
example testing via `localhost` or that machine's own LAN or Tailscale
address, still shows up as `127.0.0.1`. There's no "real" external client
to see in that case. To verify client IPs are being recorded correctly,
test from a genuinely different device.
</Aside>

## Certificate reload behavior

`nginx` doesn't start with the bare `nginx` command. It starts a small
script that:

<Steps>
1. Waits for both `fullchain.pem` and `privkey.pem` to show up in `./certs`,
   so `nginx` never fails to start just because `cert-renew` hasn't issued
   the first certificate yet, or you haven't dropped in your own cert yet.
2. Checks whether something else on the host is already listening on port
   80 or 443, and prints a specific hint pointing at Tailscale Funnel or
   Serve if so. See [the Funnel
   section](#exposing-it-beyond-your-tailnet-with-tailscale-funnel) below,
   that's the most common real cause of this on a Tailscale deploy.
3. Starts nginx, then checks the certificate file every hour and reloads
   nginx the moment it changes. nginx caches whatever certificate it loaded
   at startup and never notices a renewed file on its own without a reload.
</Steps>

That hourly check is also why a manually reissued certificate can take up
to an hour to actually take effect if `nginx` was already running. Force
it immediately with:

```sh
docker compose exec nginx nginx -s reload
```

See [Moving to a new machine](/deployment/moving-hosts/) for the scenario
this most commonly comes up in.

## CPU / worker count

Gunicorn (the process running the app inside `web`) defaults to a single
worker, which means the app never uses more than one CPU core no matter
how many the host has. RedScribe auto-sizes the worker count on startup
using the standard gunicorn formula, `(2 * cores) + 1`, unless you set
`GUNICORN_WORKERS` explicitly in `.env`. That core count respects any CPU
limit you've placed on the container (for example `docker run --cpus`),
not just the host's total core count.

This setting only affects the app process; `nginx`'s own worker count comes
from its base image and isn't something this project configures. See
[Requirements & sizing](/getting-started/requirements/) for how worker
counts map to instance tiers.

## Exposing it beyond your tailnet with Tailscale Funnel

By default, [Method 1](/getting-started/installation/#method-1-docker-compose--tailscale-recommended)
is reachable only from devices on your tailnet. To make it reachable from
the public internet too, use [Tailscale
Funnel](https://tailscale.com/kb/1223/funnel), but forward the connection
as **raw TCP**, not Funnel's default mode that terminates HTTPS itself.
`nginx` already terminates TLS with the certificate `cert-renew` issued.
If Funnel also terminates TLS and hands `nginx` decrypted HTTP, `nginx`
rejects it outright with `400 The plain HTTP request was sent to HTTPS
port`.

```sh
tailscale funnel --bg --proxy-protocol=2 --tcp=443 443
```

<Aside type="caution" title="--tcp, not --tls-terminated-tcp">
Despite the name, `--tls-terminated-tcp` means Tailscale itself strips the
TLS before forwarding, which is exactly what you don't want here. `--tcp`
passes the encrypted bytes through untouched, so `nginx` sees the real
handshake. Confirm it worked with `tailscale funnel status`, the mapping
should say plain `(Funnel on)`, not `(TLS-terminated TCP, Funnel on)`.
</Aside>

This requires Funnel enabled for your tailnet, the same admin console
toggle as HTTPS certificates. See Tailscale's own docs if `tailscale
funnel` refuses to start.

`--proxy-protocol=2` matters just as much as `--tcp` does. Without it,
Funnel still relays the connection, but `nginx` has no way to recover the
real visitor's IP, since Funnel forwards over loopback. Every request
would then show up in the [audit log](/security/audit-trail/) and login
lockout checks as `127.0.0.1` instead of the actual visitor. `nginx` is
already configured to expect this flag on its loopback listener, so
nothing else needs to change on the RedScribe side.

<Aside type="caution" title="Side effect: localhost/127.0.0.1 stop working directly">
Once that listener requires every connection to start with a proxy
protocol preamble, `https://localhost/` or `https://127.0.0.1/` from the
host itself stops working, since the request looks like a malformed
handshake to `nginx`. Use the tailnet hostname instead, same as any other
visitor would.
</Aside>

### Turning it back off

```sh
tailscale serve reset
```

This setting lives entirely in Tailscale's own daemon, not in Docker, so
it survives `docker compose down`, removing containers and volumes, even
wiping every container and rebuilding from scratch. None of that touches
it.

Left in place, it also causes a real conflict the **next** time you run
`docker compose up`: Tailscale is still holding port 443 for the Funnel
forward, so `nginx` (which needs that same port, see [Why nginx uses host
networking](#why-nginx-uses-host-networking)) fails to bind and
crash-loops with an "Address in use" error. If you hit that, `tailscale
serve status` on the host is the first thing to check.
[`watch-certs.sh`'s own startup check](#certificate-reload-behavior) also
looks for this and prints a hint pointing here before `nginx` even tries
to bind.
