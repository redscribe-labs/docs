This page covers how to upgrade a running instance without losing data if
something goes wrong, and how to roll back if it does.

<Aside type="danger" title="Upgrades run database migrations automatically, every time">
Every time the `web` container starts, it runs any pending database
migrations automatically, with no dry-run step and no automatic snapshot
first. If a new migration (or the code that shipped with it) turns out to
be broken once it's live, the only way back is the backup and restore
tooling below, and only if you took a snapshot **before** upgrading. Make
that step part of the upgrade itself, not something you reach for after
it's already gone wrong.
</Aside>

## The upgrade procedure

<Steps>
1. **Snapshot the current, known-good state before pulling anything new:**

   ```sh
   docker compose exec -T web python manage.py create_backup
   ```

2. **Pull the new version, refresh the base images, and restart:**

   ```sh
   git pull
   docker compose pull --ignore-buildable
   docker compose build --pull
   docker compose up -d
   ```

   The two middle commands fetch the latest PostgreSQL, nginx, and Python
   base images, so OS and library security fixes arrive with every upgrade.
   A plain `docker compose up -d --build` keeps reusing whatever base images
   are already on the host. If you run the Tailscale profile, add
   `--profile tailscale` to the `pull` and `up` commands.

   <Aside type="caution" title="Coming from PostgreSQL 17?">
   One release moves the `db` service to PostgreSQL 18, which cannot start on
   a 17 data directory — for that one upgrade, follow [Moving from PostgreSQL
   17 to 18](#moving-from-postgresql-17-to-18) below instead of this plain
   restart. Every other upgrade is just the steps here.
   </Aside>

3. **If something's broken**, roll the code back first:

   ```sh
   git checkout <previous-tag-or-commit>
   docker compose up -d --build
   ```

4. **Then restore the pre-upgrade snapshot from step 1** (the path was
   printed when you ran `create_backup`, or look in `BACKUP_DIR` for the
   most recent `redscribe-backup-<timestamp>.rsbk`):

   ```sh
   docker compose exec web python manage.py restore_backup /app/backups/redscribe-backup-<timestamp>.rsbk
   ```
</Steps>

Rolling the code back alone is sometimes enough, if it's a bad release with
no migration in it. You only need to restore the database once a migration
has actually changed the schema in a way the old code can't run against.
Either way, having that pre-upgrade snapshot in hand before you start means
you're never making this call under pressure with nothing to fall back on.

For the full detail on `create_backup` and `restore_backup`, including
retention, encryption, the account-reconciliation report `restore_backup`
prints before it touches anything live, and the automatic safety snapshot
it takes for you right before restoring, see [Backup &
restore](/admin/backup-and-restore/).

## Moving from PostgreSQL 17 to 18

One release moves the `db` service from PostgreSQL 17 to 18. The 18 container
image stores its cluster in a major-version subdirectory and mounts the
volume one level higher (at `/var/lib/postgresql`, not `.../data`), and it
**refuses to start on an existing 17 data directory**. So this one upgrade is
a backup-and-restore, not the plain restart above. A fresh install has
nothing to do here — it starts on 18 directly.

Do this while the instance is still running on 17:

<Steps>
1. **Back up**, and note the file it writes and your
   `BACKUP_ENCRYPTION_PASSPHRASE`:

   ```sh
   docker compose exec -T web python manage.py create_backup
   ```

2. **Stop the stack and pull the release that moves to 18:**

   ```sh
   docker compose down
   git pull
   ```

3. **Remove the old 17 data volume** so the 18 image initialises a fresh
   cluster (confirm the name first with `docker volume ls`):

   ```sh
   docker volume rm redscribe_pgdata
   ```

4. **Start again** — the 18 server comes up empty and `web` applies every
   migration (add `--profile tailscale` if that's how you run it):

   ```sh
   docker compose up -d --build
   ```

5. **Restore the step 1 backup** (it writes its own pre-restore safety
   snapshot first):

   ```sh
   docker compose exec web python manage.py restore_backup /app/backups/redscribe-backup-<timestamp>.rsbk
   ```
</Steps>

Removing the volume in step 3 deletes the 17 data for good, so the step 1
backup is your only way back — keep it until you've confirmed the restored
instance works.

## Version tags

Releases are tagged `v<version>` (for example `v0.2.0-alpha`). The
`git checkout <previous-tag-or-commit>` in step 3 above means exactly that
tag, or any commit you know was working. See [Alpha status &
versioning](/start/alpha-status/) for how RedScribe's pre-1.0 versioning
works and what to expect from a minor-version bump.
