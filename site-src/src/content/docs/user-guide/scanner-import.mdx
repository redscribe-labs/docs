If you've already run Nmap, Burp Suite, or Nuclei against a target, you don't have to retype every result by hand. From an engagement, open **Findings** then **Import**, and upload the scanner's raw output file to bulk create draft findings instead of entering them one at a time.

This option only appears if your administrator has turned on scanner import for the instance. If it's off, you won't see the screen at all.

The upload form accepts any file up to 75MB, and doesn't check the file's extension or content beyond that size limit. That means the format you pick from the dropdown is what actually decides how the file gets parsed. Uploading a Burp XML file while "Nuclei JSON Lines" is selected will fail with a parse error rather than a helpful "wrong tool" message, since RedScribe has no way to know what you meant to upload.

## What each parser extracts

All three parsers turn scanner output into a list of draft findings, each with a title, a severity, an affected assets string, technical details, and optionally a CVE ID and classification tags. None of them read a scope or target list from the file: every open finding, port, or issue in it becomes a finding, so trim your scan output first if you only want a subset imported.

### Nmap (XML, from `nmap -oX`)

The parser walks every host in the file and every port that's open. For each open port:

- If a script Nmap ran against that port flagged it as vulnerable, a finding is created for each flagged script: High severity, with the script's raw output as technical detail, and a CVE ID pulled out automatically if one appears in that output.
- If the port is open but nothing flagged it as vulnerable, a finding is still created, just as an Informational "Open port" finding recording the service and version banner Nmap detected. Open ports are never silently dropped just because nothing was flagged.

Every finding from this parser is tagged so you can filter or report on Nmap results specifically later.

<Aside type="tip" title="Getting vulnerability findings to appear at all">
A plain Nmap scan with no vulnerability scripts run will only ever produce "Open port" informational findings. To get actual vulnerability findings out of the import, run Nmap with a vulnerability scanning script set first, for example `nmap -oX scan.xml --script vuln target`, and then import the resulting file.
</Aside>

If the uploaded file isn't a valid Nmap XML report, or the host has no open ports anywhere in it, the import is rejected with a clear error rather than silently creating nothing.

### Burp Suite (XML, from Issues → Report as XML)

The parser reads every issue in the report. Burp's severity levels map onto RedScribe's scale directly (High to High, Medium to Medium, Low to Low), and both "Information" and "False Positive" come in as Informational, a false positive isn't dropped, it just lands as an informational finding you can archive or delete after review. The finding's technical details pull together whichever detail, background, and remediation text Burp recorded for that issue, each clearly labeled. All findings from this parser are tagged so you can filter or report on Burp results specifically later.

If the file isn't a valid Burp Suite XML report, or it parses but contains no issues, the import is rejected with a clear error.

### Nuclei (JSON Lines, from `nuclei -jsonl`)

This format is read one result per line, matching Nuclei's native output shape. Per result: the title, severity (critical, high, medium, low, or info, with anything else or missing treated as Informational), CVE ID if present, and every tag Nuclei recorded become a classification. Technical details combine the template used, its description if present, and what was matched.

If any single line fails to parse, the whole import is rejected with an error naming the exact line and what went wrong. One malformed line fails the entire file, nothing partial gets imported. If the file has no results in it at all, the import is rejected with a clear error too.

## Where the description text lands

Every parser's technical details text is written into whichever [content section](/admin/finding-structure/) your instance has marked as the import target, if any. If no section is marked that way, the parsed detail text is simply discarded: the finding is still created with its title, severity, affected assets, CVE ID, and tags, just with an empty body. If your imports keep showing up with no description, this is the first thing to check with your administrator.

## Every import lands as Draft

Nothing skips the normal [review workflow](/user-guide/findings/#the-review-workflow) just because a finding came from a scanner. A hundred findings imported at once are still a hundred findings sitting in Draft, waiting to be reviewed and QA approved like any other.

## What gets recorded

Each import creates a record regardless of whether the parse found one finding or a hundred: which tool, the filename, the date, who imported it, and how many findings it produced. This is what appears in the report's scan imports appendix, and it's the only trace of the import that survives past the upload itself.

<Aside type="caution">
The original uploaded scan file is never stored, only this summary record. If you need the raw scan output later, for example to re-verify a result or re-import with different settings, keep your own copy outside RedScribe. There's no way to re-download a past import from within the app.
</Aside>
