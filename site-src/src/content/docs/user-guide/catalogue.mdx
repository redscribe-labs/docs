The catalogue is a shared library of pre-written vulnerability templates your whole team draws from, so common findings don't get rewritten from scratch on every engagement.

## Who can do what

Anyone signed in can create a draft catalogue entry, and anyone can edit or delete an entry they created themselves with no special permission at all, the same way you can always edit your own draft. Touching someone else's entry is where permissions come in: some let you edit or delete any entry, others let you approve entries or move them through QA, and one unlocks whole-catalogue export and import. See the [Permissions reference](/reference/permissions/) for the exact list if you're setting up roles.

## The workflow

```
Draft ──submit for QA──▶ Pending QA ──approve──▶ Approved
```

Only an entry that's currently **Approved**, or one that used to be approved and still has that approved version on file, can be imported into a finding. See [Creating a finding](/user-guide/findings/#creating-a-finding).

### What a catalogue entry stores

A title, a default severity, an optional default CVSS score and vector, one or more classification tags, and a block of rich text for each active [content section](/admin/finding-structure/) your instance uses (vulnerability description, business impact, and so on). There's no separate "notes" or "author" field beyond that. Whoever created the entry is tracked for permission purposes, but it isn't shown as a byline anywhere.

## Editing an entry that isn't a fresh draft

Saving an edit to an entry that's Pending QA or Approved resets it straight back to Draft, every time, and tells you so. This applies even to a small wording fix; there's no "minor edit" exception. If you edit an Approved entry, it drops all the way to Draft rather than back to Pending QA, so it has to go through the full submit-for-QA step again before it can be re-approved.

### How the approval snapshot works

Approving an entry doesn't just flip a status label. It also saves a complete, frozen copy of the entry, title, severity, CVSS fields, classifications, and every section's content, in a separate record. That snapshot, not whatever the entry currently looks like, is what actually gets pulled in when someone imports it into a finding. Re-approving replaces the snapshot; it isn't versioned history.

That separation is what makes the catalogue safe to edit while other people are using it. The moment you start editing an Approved entry, its status drops to Draft, but the snapshot from its last approval stays exactly as it was. Anyone importing from that entry in the meantime still gets the vetted, approved content, not your unfinished edit, right up until someone approves the new version.

Explicitly reverting an entry from Approved back to Draft (rather than just editing it) is different: it also deletes the snapshot outright, which immediately makes the entry un-importable until it's approved again. So if a catalogue entry shows as importable while its status reads Draft or Pending QA, that's expected: you're looking at the in-progress content, but importing would still pull the last approved version instead.

## Import and export

Export produces a single JSON file with one entry per catalogue template, including title, severity, CVSS fields, classification tags, and each content section's rich text. It's meant for moving a catalogue between RedScribe instances or keeping an external backup, not as something you'd hand-edit day to day.

Importing checks every entry before creating anything: a title is required, severity has to be one of RedScribe's real severity values, any CVSS vector has to parse correctly, and every classification needs both a taxonomy and a value. A single bad entry anywhere in the file rejects the whole import, naming which entry and field failed, so nothing partial gets created.

<Aside type="danger" title="Import never updates or merges existing entries, it always creates new ones">
There's no matching on title or anything else. Importing the same file twice produces two full sets of duplicate entries. If you're re-importing an updated version of a catalogue you exported earlier, expect duplicates rather than an in-place update, and clean up the old entries yourself if that's not what you want.
</Aside>

A content section in the imported file that doesn't match any section your instance currently uses is silently skipped, so importing a catalogue exported from a differently configured instance can quietly drop content you'd expect to see, without telling you it happened. Every imported entry lands as a fresh **Draft** regardless of whether the export captured it as Approved, so imported content always goes through your instance's own review process from scratch.

<Aside type="note">
A fresh RedScribe instance ships with an empty catalogue. Nothing is pre-loaded, so build it up over time or import one.
</Aside>
