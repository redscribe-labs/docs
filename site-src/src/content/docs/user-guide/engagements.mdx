An engagement is the container for one client project, a web application pentest, a network assessment, a vulnerability scan, or a remediation retest. Everything else in RedScribe (findings, checklist runs, scanner imports, the report) hangs off one engagement.

## The engagements list

**Engagements** lists every engagement you can see, with tabs for each status and how many engagements are in it. Each row shows the client and reference, test type, status, testing window, open findings by severity, and checklist coverage. Search matches client names and reference numbers.

## Creating an engagement

From **Engagements**, select **New engagement**. You'll need the right permission to create one; see the [Permissions reference](/reference/permissions/) if you're setting up roles.

<Screenshot src={shotEngagementCreate} alt="The new engagement form with client, reference number, test type, dates, default reviewer, QA and approver" />

You'll fill in:

- **Client**, which must already exist as a [client company](/client-portal/managing-clients/). You can't create an engagement against a free-typed client name.
- **Reference or project number**.
- **Start and end dates**.
- **Test type**: Web Application, Network, or Vulnerability Scan.
- **Default reviewer, QA, and approver** (optional), assigned automatically as findings move through review.
- **Testing checklist**: the checklist template to start a run from straight away. It's pre-set to your default template; choose **Don't start a checklist yet** to skip it. See [Checklists](/user-guide/checklists/).

Everything except the client can be changed later on the engagement's **Settings** tab.

<Aside type="note">
Linking to a real client company, rather than just typing a name, is what makes [client portal](/client-portal/for-clients/) access and cross-engagement [trend reporting](/user-guide/trends-and-search/) by client possible.
</Aside>

## Scope and asset groups

Scope is structured, not free text. You define it after creating the engagement, from **Manage scope** on the overview (managers only — the same permission that edits the engagement).

Scope has two levels:

- **Asset groups** — named buckets you order yourself, typically **Internal** and **External**, but name them to match the job. A group is what a network-penetration-test report splits its findings on (see below).
- **Scope assets** — the in-scope targets under a group. Each has a **type** (URL, IP, subnet, or FQDN), the **value** itself, and an optional **notes** field for inclusion caveats.

<Steps>
1. Open **Manage scope**, add one or more asset groups (for example `Internal` and `External`).
2. Add scope assets under each group, choosing a type and entering the value.
3. The engagement overview and the [client portal](/client-portal/for-clients/) then show scope as a table per group, and reports can render it with the `scope_table` tag.
</Steps>

<Screenshot src={shotManageScope} alt="The Manage scope page: a Scope assets table with Group, Type, Asset, and Notes columns listing Internal and External assets, an Add an asset form below, and an Asset groups panel on the right for adding or removing groups" caption="Manage scope: asset groups on the right, the typed scope assets under them on the left." />

Asset groups do two jobs beyond documenting scope. When the engagement's [report profile](/admin/report-profiles/#splitting-findings-by-asset-group) is set to **split findings by asset group**, every [finding](/user-guide/findings/#asset-group) is tagged with one, and the report produces a separate findings section per group (Internal, External, …) over a single combined severity chart. On any other profile, asset groups are just scope documentation and findings aren't tagged.

<Aside type="note">
The free-text scope field from earlier versions is gone. Existing scope text is migrated into a single **In Scope** asset group on upgrade, which you can then split up. See the [0.8.0-alpha changelog](/changelog/) for the breaking-change details.
</Aside>

## Status lifecycle

<Screenshot src={shotEngagementDetail} alt="An engagement's overview: a status bar across every stage, the next status changes as buttons, a Ready to publish checklist, coverage figures, the structured scope by asset group, team, who has access, and the client portal card" caption="The overview shows where the engagement is in its lifecycle and what's left before it can be published." />

An engagement moves through a fixed sequence of statuses. The overview shows them as a bar with the current stage highlighted, and offers the next status changes as buttons at the top; each asks you to confirm before it changes anything:

```
In Progress → In Review → QA → Approved → Delivered
                                              │
                                              ▼ (if remediation testing is needed)
                                   Awaiting Remediation Test → Remediation Test → Closed
```

**Ready to publish?** on the overview tracks the three things that usually gate delivery: every finding is ready to publish, the checklist has an outcome for every check, and the engagement is released to the client portal.

QA approval is a hard gate, not just a reminder: moving an engagement from **QA → Approved** or from **Approved → Delivered** is blocked unless every active finding is QA-approved. The block names how many findings still aren't there. [Archived findings](/user-guide/findings/#archiving) are excluded from the check, so a finding you've deliberately set aside won't hold up delivery.

Every status change is recorded in the engagement's history: who made it, when, and what it changed from and to. That history is what feeds the document control section of the generated report. Changing status needs the same permission as editing the engagement's own details.

## Membership

Add or remove members under **Who has access** on the engagement's overview. The **Team** card shows the default reviewer, QA, and approver. Membership controls who can see and work on the engagement, unless you hold broader visibility across every engagement. Members are also exactly who the report's Assessment Team section pulls its bios and qualifications from, so keep membership current if you want the right names on the cover.

<Aside type="caution">
RedScribe is built around at most two people actively working on the same engagement's data at a time. See [Requirements & sizing](/getting-started/requirements/#what-shifts-these-numbers). Membership isn't a hard access lock beyond that; it's mainly about visibility and assignment.
</Aside>

## Scope changes

Scope changes go through an approval step, so there's a defensible record of what was actually agreed to mid-engagement before anyone edits the live scope.

<Steps>
1. On the engagement's overview, under **Scope**, open **Propose a scope change**, describe the change, and select **Submit for Team Lead approval**.
2. Someone with the right permission **approves** or **rejects** it. Both outcomes are kept as part of the engagement's history.
3. Approval records the decision and notifies — it does not edit the scope itself. A manager then applies the agreed change on [**Manage scope**](#scope-and-asset-groups), adding or removing asset groups and assets to match.
</Steps>

## Archiving and deletion

- **Archive** soft-deletes an engagement. It drops out of the default engagement list, but nothing is actually destroyed. **Unarchive** reverses it.
- **Permanent delete** is reserved for the highest level of administrator, and only works on an engagement that's already archived. It's the one deliberate exception to RedScribe's usual archive-instead-of-delete approach, meant for genuine data retention purges rather than everyday cleanup. It removes the engagement from the live database only; a backup taken before the deletion still contains it until that backup is separately pruned or overwritten. See [Backup & restore](/admin/backup-and-restore/#permanently-deleted-data-can-still-exist-in-a-backup) if a retention or disposal requirement means it needs to be gone from every copy.

## Releasing to the client portal

Findings never show up in the [client portal](/client-portal/for-clients/) just because they exist. An engagement has to be explicitly released with **Release to client portal**, on the **Client portal** card of its overview, and even then, only findings that have individually cleared QA are shown. **Revoke client release** reverses it, hiding the engagement from the portal again immediately.
