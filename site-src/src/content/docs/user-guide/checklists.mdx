RedScribe separates **templates**, reusable test lists you manage once, from **runs**, one working copy of a template against a specific engagement.

## Templates

Anyone can view the template library. Creating, editing, or managing items needs a separate permission; see the [Permissions reference](/reference/permissions/) if you're setting up roles.

- **Create** a template from scratch and add items one at a time (category, code, title, reference info), with full editing, reordering, and a **default** flag that marks a template as the one pre-selected when someone starts a new run.
- **Upload** a template through JSON or CSV bulk import instead of entering items by hand.
- **Export** any template back out to JSON.

<Aside type="tip">
A fresh instance ships with zero templates. Nothing is pre-loaded, so pick your own by importing. The RedScribe repository includes a ready-to-import template covering the full official OWASP Web Security Testing Guide, each item's objectives plus a link back to the official page, if you want that as a starting point. See the [checklist template format](/reference/checklist-template-format/) reference to build your own.
</Aside>

## Runs

From an engagement, open **Checklist**. An engagement can have multiple independent runs going at once, for example OWASP WSTG against a web app alongside the OWASP API Top 10 against its API, on the same engagement.

Each item's status is one of:

| Status | Meaning |
|---|---|
| Not Tested | Default, not yet worked |
| Tested — No Finding | Tested, nothing to report |
| Tested — Finding Raised | Tested, and linked to one or more findings |
| Not Applicable | Out of scope for this engagement |

Working an item:

<Steps>
1. Open the item. Sequential next/previous navigation moves you through the run in order without bouncing back to the list each time.
2. Record test results and set its status. Like other sensitive engagement content, results are encrypted at rest; see [Encryption model](/security/encryption/).
3. Link any findings this item raised. This is what lets the report's checklist coverage section group runs by category and cross-reference the findings tied to each one.
4. Leave a comment on the item if useful context doesn't belong in the result itself.
</Steps>

## Exporting a run

**Export** on a checklist run produces a JSON export of its full testing data, including objectives, results, linked findings, and comments, independent of the report itself.
