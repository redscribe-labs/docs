Every request against RedScribe is recorded in an audit log that's built
so that tampering with it, even by someone with direct database access,
leaves detectable evidence behind. This page explains how that works. For
the operational side, viewing entries, running a purge, setting up cron,
see [Audit log](/admin/audit-log/).

## What gets logged

Almost every request is logged, not just the ones that change data.
Ordinary page views and API reads are recorded too. A small number of
high-frequency or non-sensitive endpoints are excluded by design: the
report live-preview endpoint (which would otherwise flood the log on every
keystroke of report configuration), the health check, and the CSP
violation-report endpoint. Every login attempt, successful or not, is
recorded separately; see [Authentication & sessions](/security/authentication/)
for how that feeds into lockout.

Each entry records who did it (user, username, and their role at the time,
kept even if the user is later deleted), what they did (the action, HTTP
method, path, and status code), which engagement it touched, the client
IP, query string, referer, user agent, and how long the request took.

### What's redacted before it's ever written

A handful of fields are sanitized before an entry is written, so a
sensitive value is never at rest in the log in the first place, rather
than being redacted after the fact:

- Password-reset and account-setup links have their token stripped out of
  the stored path.
- Any query string parameter whose name looks like `token`, `password`,
  `secret`, `key`, `otp`, `auth`, `signature`, or `credential` has its
  value replaced, regardless of what the parameter is actually for.
- A referer URL that contains something that looks like a bearer token
  gets that segment redacted the same way.
- Query string, referer, and user agent are all capped at a few hundred
  characters each, redacted or not, so a single request can't bloat an
  entry.

## The hash chain

Each audit entry's integrity hash is computed by folding together its own
fields, plus the hash of the entry immediately before it, using a keyed
HMAC (not a plain hash) so the hash can't be recomputed by someone without
access to the server's own signing key. The example below shows what goes
into that computation, in order, for a single entry:

```python
canonical = "|".join([
    prev_hash, pk, created_at, actor_id, actor_username, actor_role,
    action, method, path, status_code, engagement_id, object_ref,
    ip_address, query_string, referer, user_agent, duration_ms,
])
entry_hash = HMAC-SHA256(key=<server signing key>, msg=canonical)
```

The very first entry ever written chains onto a fixed, well-known starting
value. Because each entry's hash folds in the one before it, changing
*any* field on *any* row, including by editing the database directly
rather than going through the app, changes that row's hash. That, in turn,
breaks the chain for every row written after it. The tamper is detectable
anywhere downstream of the edit, not just on the row that was actually
changed.

<Aside type="caution" title="Rotating the server's secret key breaks verification of old entries">
The hash chain is keyed with the same secret Django uses for other signing
purposes. If you rotate that secret on a running instance, every
previously written entry will fail verification, because verification
always checks against the *current* key. That's expected, not a bug, but
it means you should think about the effect on historical audit
verification before rotating it.
</Aside>

### Concurrency safety

Appending a new entry takes a database-level lock first, so that two
requests arriving at the same time can't both read the same "last entry,"
compute a hash against it, and insert two entries that both claim to
follow the same predecessor. Writes to the chain are serialized, even
under concurrent load.

## Verifying the chain

```sh
docker compose exec web python manage.py verify_audit_log
```

This walks every entry in order, recomputing each one's expected hash and
comparing it to what's stored. It fails loudly, with a non-zero exit code,
the moment a stored hash doesn't match, and names the first entry where
that happened.

The oldest surviving row is a special case, since there's nothing earlier
to check its `prev_hash` against. The command reports it as an anchor
rather than a failure, and tells you which of two things is going on:

- If its hash matches what you'd get from the fixed starting value, it's
  genuinely the first entry ever written.
- Otherwise, it's flagged as an oldest surviving row whose earlier history
  may have been purged, which is expected after a legitimate
  [retention purge](/admin/audit-log/#retention), not a sign of tampering.

## Partitioning and retention

The audit log is stored as one partition per calendar year, created ahead
of time:

```sh
python manage.py create_audit_partition            # creates next year's partition
python manage.py create_audit_partition --year 2028 # or a specific year
```

That structure makes retention cheap: purging drops an entire year's
partition at once when it's fully past the retention cutoff, rather than
deleting rows one at a time, and only falls back to row-by-row deletion
for a partition that's partially expired. The same purge also removes old
login-attempt records on the same schedule. By default, entries are kept
for 6 years, matching HIPAA's general documentation-retention guidance.
See [Audit log](/admin/audit-log/) for tuning that to your own compliance
obligations.
