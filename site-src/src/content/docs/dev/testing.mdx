## Running the suite

```sh
python manage.py test
```

Run this from a [Method 4 local dev](/dev/local-development/) environment,
since it needs the same `DJANGO_SETTINGS_MODULE=config.settings.dev`,
database connection, and root key as `runserver` does. The suite is
DB-backed. Django creates and tears down a throwaway test database
automatically around the run, so it never touches your real development
data.

### Running a subset

Django's test runner accepts a dotted path, so you can scope a run to
exactly what you're working on instead of the full suite:

```sh
python manage.py test apps.findings              # one app
python manage.py test apps.findings.tests.FindingViewTests            # one test class
python manage.py test apps.findings.tests.FindingViewTests.test_create_requires_permission  # one test method
```

This is worth using while iterating. The full suite takes real time to run
against a real Postgres instance, and there's no need to pay that cost on
every save while you're working inside a single app.

## Testing style

Every app has exactly one `tests.py` at `apps/<app>/tests.py`, following
Django's default test discovery convention rather than a separate `tests/`
package per app. There's no `pytest`, no `factory_boy`, and no fixture
files. Every test is a plain `django.test.TestCase` subclass grouped by the
feature it covers (for example `apps/findings/tests.py` has
`FindingViewTests`, `CommentThreadTests`, `CatalogueTests`,
`CatalogueVersioningTests`, and so on, each with its own `setUp()` building
whatever engagement, finding, or user state that group of tests needs from
scratch). Most tests exercise real views through Django's test `Client`
rather than calling internal functions directly, so they cover permission
checks, redirects, and template rendering the same way an actual request
would. As of this writing the suite has 900+ individual test methods across
all apps. Run `grep -rc "def test_" apps/*/tests.py` from the repo root for
an exact current count, since it only grows over time and any number given
here should be treated as a lower bound rather than the real figure.

<Aside type="note">
There is no linter or formatter wired into CI, no `ruff`, `black`, `flake8`,
or `mypy` configuration anywhere in the repo. Code style is enforced by
convention and review, not by a tool. Don't go looking for a pyproject.toml
lint section, there isn't one.
</Aside>

## No CI — run these checks yourself

There is currently **no CI**. A `.github/workflows/test.yml` workflow ran
these checks automatically for a while, but was removed: with no CI runner
to diagnose failures against, a broken workflow was just producing
failure-notification emails with no way to see why, and the suite runs
identically well locally. Run both of these before opening a PR:

```sh
python manage.py makemigrations --check --dry-run
python manage.py test
```

**The migration check matters on its own.** It catches a model change with
no migration file committed immediately, rather than as a confusing
downstream test error partway through the suite.

Test against a real `postgres:17-alpine` database, not SQLite. RedScribe's
suite leans on real Postgres row-locking behavior in several places
(encryption, the audit hash chain, the report job slot limiter) that a
lighter-weight substitute wouldn't exercise faithfully. [Local
development](/dev/local-development/) already sets this up for you.

## What a PR is expected to include

Per [Contributing](/dev/contributing/), a PR that changes behavior should
come with tests covering it, written in the existing style of the relevant
app's `tests.py` rather than introducing a new testing pattern for just
that one change. Run the suite locally before opening the PR — there's no
CI running it again for you, so this is the only check a PR gets.
