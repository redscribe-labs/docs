RedScribe keeps a hash-chained record of everything that happens on your
instance, request by request, and login attempt by login attempt. This
page covers what's in it, how to browse it, how long it's kept, and how to
check its chain hasn't been altered. See [Audit trail &
integrity](/security/audit-trail/#limitations) for exactly what that chain
does and doesn't catch.

**Audit Log** in the sidebar needs its own permission to manage. It
records **every request**, including plain page views and not just the
ones that change something, plus every login attempt. Each entry captures
who did it (user, username, and their role at the time), what they did,
the HTTP method and path, the response status, any related engagement or
object, their IP address, query string, referring page, browser, and how
long the request took.

Almost everything is logged. The only exceptions are a short, fixed list
of things that would just add noise: the health check endpoint and the CSP
report endpoint, plus bare `HEAD`/`OPTIONS` requests. Two sensitive URLs,
the password reset and account setup confirmation links, have their path
redacted in the log, since the URL itself contains a single-use token
that shouldn't sit around readable.

## Browsing and filtering

The Audit Log page is filterable by free-text search (matches actor
username, action, path, object reference, IP, browser, or referring page),
HTTP method, actor, status-code bucket (2xx/3xx/4xx/5xx), and a from/to
date range, with a configurable page size.

## Retention

Entries are kept for a configurable window, six years by default. That
default matches HIPAA's general documentation-retention rule, and is the
most conservative of the commonly-referenced regimes for this kind of
tool. Override it to match your own compliance obligations if six years
isn't the right number for you.

Purging is **never automatic**, since nothing in RedScribe runs on a
schedule of its own. Wire it into your host's own cron for a
self-maintaining instance:

```sh
0 3 * * * cd /path/to/redscribe && docker compose exec -T web python manage.py purge_audit_log
```

Add `--dry-run` to preview the delete count first, or `--days N` to purge
against a one-off window instead of the configured default. Whoever
manages the audit log can also trigger the same purge on demand from the
**Purge entries older than N days** button on the Audit Log page. It's the
same underlying logic either way, and the purge action itself is recorded
in the audit trail like any other state-changing request.

<Aside type="tip">
Purging drops whole year-long chunks of the log at once wherever an entire
year is already past the cutoff, falling back to row-by-row deletion only
for the partial year straddling the cutoff. That means a routine purge on
a mature instance is a fast operation, not a slow full scan. Login-attempt
records older than the same cutoff are purged in the same pass.
</Aside>

### Clearing everything

Separate from the age-based purge above, the Audit Log page also offers
**Clear all logs**, an unconditional wipe of every audit log and
login-attempt row, regardless of age. Because this is destructive,
irreversible, and the one action that erases audit history outright, it
needs two things, not one: the exact phrase `DELETE ALL LOGS` typed into a
confirmation field, **and** a second, currently active Superadmin's own
username and password entered on the same page. That second Superadmin
has to be a genuinely different account from whoever is doing the
clearing; nothing is deleted otherwise. There's no equivalent one-step
shortcut for it.

## Chain integrity

Every entry is cryptographically chained to the one before it, so
changing a stored row anywhere in the chain, including through direct
database access rather than the app, invalidates every hash that comes
after it. A brand-new instance's very first entry chains from a fixed
starting value. See [Audit trail &
integrity](/security/audit-trail/#limitations) for what this does and
doesn't catch, deleting rows is a different case from editing one in
place.

Check the whole chain at any time with:

```sh
docker compose exec web python manage.py verify_audit_log
```

The oldest surviving row can't be checked against a prior link. Either
it's genuinely the first entry ever, or everything before it was
legitimately removed by a retention purge. The command reports that row
as an **anchor**, not a failure, and flags the first row after it (if any)
whose recomputed value doesn't match what's stored.

<Aside type="danger" title="This proves the chain wasn't altered through the database, not a public signature">
Verifying the chain requires the same secret the app itself uses
internally. It proves the chain hasn't been altered by anyone going
through the database directly without also knowing that secret. It isn't
designed as a proof you'd hand to an external auditor to check
independently, without also handing them a sensitive credential you
otherwise wouldn't share.
</Aside>
